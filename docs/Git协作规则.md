# 「食觅」开发协作规则 V1

适用范围：3 人小团队，基于 `tonight-menu` fork 而来的私有仓库，微信原生小程序 + 云开发(CloudBase)。

## 1. 仓库与分支

- 仓库：由 BOBO fork `tonight-menu` 到自己账号下，设为 **私有仓库**，其余两人以协作者(Collaborator)身份加入，拥有 push 权限。
- 分支策略：**GitHub Flow**（不用 Git Flow，太重）。
  - `main`：随时保持可运行状态，不允许直接 push，只能通过 Pull Request 合并。
  - 功能分支：从 `main` 拉出，命名规则见下。
  - 功能开发完、自测通过 → 发 PR → 至少 1 人 review → 合并进 `main` → 删除该分支。

## 2. 三人角色与分支命名

按角色横向分工，分支名前缀标明角色，方便一眼看出改动范围：

| 角色 | 负责内容 | 分支前缀示例 |
|---|---|---|
| 前端 | 小程序页面 UI、交互、`pages/` 目录 | `feature/fe-首页筛选` |
| 云函数 | 业务逻辑、匹配算法、审核逻辑、`cloudfunctions/` | `feature/cf-厨具过滤` |
| 数据 | 数据库集合结构、初始化脚本、测试数据、环境配置 | `feature/data-初始化脚本` |

规则：

- 每个分支只做一件事，别把三个角色的改动混在一个分支里。
- 分支存活时间尽量不超过 1 周，太久没合并就每天从 `main` 拉一次更新，避免最后冲突一大坨。
- 涉及跨角色的改动（比如云函数改了返回字段，前端要跟着改），提前在群里说一声，别默默各改各的。

## 3. Commit 信息规范

统一前缀，方便看日志：

```
feat: 新增食材勾选页
fix: 修复厨具过滤未排除已下架菜品
data: 更新预置菜谱测试数据
docs: 更新AI上下文文件
```

## 4. Pull Request 与 Review

- PR 标题写清楚"改了什么"，不要只写"update"。
- 至少让另外 1 人看一眼再合并，哪怕只是扫一眼逻辑对不对，避免自己审自己。
- 合并方式统一用 **Squash and merge**，保持 `main` 的提交历史干净。
- 合并冲突较大时（多发生在 `dishes` 集合字段结构变动上），三人一起对着屏幕解决，不要一个人硬合。

## 5. 云开发环境协作

- 三人**共用同一个云开发环境**（由 BOBO 名下账号创建），另外两人在微信开发者工具里通过"环境共享"加入。
- **一人担任管理员**（负责审核投稿、维护 openid 白名单），另外两人是普通用户角色，本地联调时用各自微信号登录测试。
- 环境 ID、AppID 等配置信息**不要提交进代码仓库**：`project.config.json` 里涉及个人身份的部分和云环境 ID 建议抽到一个不进 git 的本地配置里，`.gitignore` 里加上，避免密钥/环境信息泄露。
- 谁改了数据库集合结构（加字段、建新集合），必须在群里同步一句，并更新 AI 上下文文件里的字段说明，否则其他两人本地代码会因为字段对不上而报错。

## 6. 现有代码怎么处理

`tonight-menu` fork 过来后，`pages/fatloss`、`ingredients`、`recommendations` 等页面已有实际逻辑，**不是空壳**。第一步统一动作：

1. 三人先各自过一遍现有代码，搞清楚哪些逻辑能直接复用、哪些和规划书 V1 设计冲突。
2. 在 AI 上下文文件里补一段"现状说明"，标出"已复用"和"待重写"的模块，避免 AI 后续瞎改能用的代码。
3. 不要一上来就大改，先跑起来、能看到效果，再按分工逐步替换。

## 7. 测试数据初始化

- 规划书要求预置 20-30 条测试菜谱，由负责"数据"角色的人写一个初始化脚本（通过云函数或云开发控制台批量导入），不要手动一条条在控制台敲。
- 脚本存放在仓库里（比如 `scripts/seed-dishes.js`），方便任何人重新初始化环境，也方便以后加测试数据时复用。

## 8. 禁止事项

- 不直接 push `main`。
- 不把云开发环境 ID、管理员 openid、任何密钥提交进 git。
- 不在一个 PR 里混跨角色的大改动。
- 不跳过 review 直接合并有争议的改动。
